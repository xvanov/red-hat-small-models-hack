# Evaluation method

How the operator agent is scored, what the numbers can and cannot support, and how to reproduce them. Written for the judges. Results themselves live in `docs/results.md`; this page is about how far to trust them.

## 1. What is fixed

- **Tasks.** `gym/tasks/{train,heldout}.jsonl` (v1: 51 train, 31 held-out) are generated by `gym/build_tasks.py` with fixed seeds, and regenerating reproduces them byte for byte (a test checks this). Every committed result used v1. Task set v2 (`gym/tasks/v2/`, 54 / 33) fixes flaws found in a review (`docs/task-review.md`, `docs/task-v2-changes.md`). The owner approved it (D23), and the quotable results are the v2 section at the top of `docs/results.md` (3 seeds per config, 2026-10-18).
- **Scorer.** `gym/rentus_env/verify.py` has 7 check types: world state, never-do rules, style, tool called, escalated, budget, message content. Each check passes or fails. A task's reward is the fraction of its checks that pass, and a task passes only if every check passes. Each config is a named variant in `gym/ablate.py`, and the scorer and tasks were never edited to suit one.
- **Eval config.** Temperature 0.2, at most 30 steps per task, the same tool backend, and the reader pinned to the rule-based fallback unless a row says otherwise. The run's git commit, RunConfig, task version and (new) task file and operator seed are recorded in each `summary.json`.
- **Solvability.** A privileged reference player (`gym/oracle.py`) passes every task (31/31, 51/51, v2 33/33, 54/54). So a failure is the agent's, not an impossible task. It does not prove the checks are the *right* ones; see section 7.

## 2. Train vs held-out discipline

- Renter lines in held-out tasks come only from the reader's published `test.jsonl`, and train lines only from `train.jsonl` (asserted, no overlap). Rooms (odd vs even inventory index) and template pools are disjoint too.
- Every harness or prompt change was designed from **train** transcripts only. `gym/results/_p21/diagnose.py` refuses to run on held-out. Changes were chosen by their train score, and held-out was run only after a change was kept. No held-out transcript was read while designing changes.
- What this does not protect against: the held-out set is small (31 tasks) and was run many times (about 15 configs). Picking the best of many configs on the same 31 tasks inflates the winner a little, even with no held-out tuning. The Holm correction in section 4 is the guard for that.

## 3. Repeats and seeds

- The model samples at temperature 0.2, so two identical runs differ. Between the two runs of the final config, **6 of 31 tasks flipped** between pass and fail. A single run is one draw, not "the" score.
- `gym/run_seeds.py` runs one config K times. Each repeat is an ordinary run dir (`results/<prefix>-s<seed>/`), and the operator seed goes out as the OpenAI `seed` field on every model call (vLLM honors it per request). The same seed and the same inputs give the same sample on one server, apart from small numeric differences when other requests share the batch. So seeds make repeats **distinct and labeled**. They do not make runs bit-identical under load.
- Rollouts that never reached the model (endpoint outages) are rerun, and the run records which ones (`model_error_retries`). A rollout that reached the model is never rerun.
- Committed v1 repeats: the baseline, `guard+prompt3+style`, the final config and final + fine-tuned reader have 2 runs each. Every other row is 1 run.

## 4. Statistics (`gym/stats.py`)

**The task is the independent unit.** Repeats reduce the noise *within* a task but add no new tasks. So every interval and test resamples or counts the 31 tasks, never the 62 task-runs.

| quantity | definition | interval / test |
|---|---|---|
| pass rate | mean over tasks of the task's pass fraction across runs | 95% Wilson, n = number of tasks (conservative with repeats) |
| mean reward | mean over tasks of the task's mean reward | 95% percentile bootstrap over tasks, 10,000 resamples, fixed seed |
| pass^k | τ-bench convention: the chance a task passes in **all** k runs, estimated per task as C(c,k)/C(n,k) and averaged | bootstrap over tasks |
| pass@k | the chance a task passes in **at least one** of k runs, 1 − C(n−c,k)/C(n,k) | |
| run-to-run sd | standard deviation of per-run pass rate and mean reward | needs 2+ runs |
| paired A vs B | same tasks: per-task difference in mean reward | paired bootstrap CI, two-sided p from the centered bootstrap |
| paired pass/fail | tasks where A's pass fraction is higher vs lower | exact two-sided sign test. With 1 run per config this **is** the exact McNemar test |
| many comparisons | | Holm-adjusted p across all comparisons in one call |

pass^k is the reliability number: a renter-facing agent that passes a task only half the time is not one you would deploy on it. pass@k is the ceiling a retry policy could reach.

```bash
gym/.venv/bin/python gym/stats.py --md --categories --config final=RUN1,RUN2 --config base=RUN3,RUN4 --compare final:base
gym/.venv/bin/python gym/stats.py --matrix --md --config final=RUN1,RUN2      # per-task pass matrix
gym/.venv/bin/python gym/run_seeds.py --variant guard+prompt3+style+rhist --split heldout --seeds 1,2,3 --prefix seeds-final
```

What holds up and what doesn't:

- **Holds up: final beats baseline**, by a lot. +0.47 reward, 22 tasks pass that never passed before, 0 the other way, and it survives any correction. Prompt v3 alone also clearly beats baseline, on both reward and pass/fail. The guard and reasoning history each raise reward significantly on their own, but neither clearly changes how many tasks pass.
- **Holds up: prompt v3 transfers to NeMo's harness.** 12 tasks improve and 1 gets worse; on pass/fail it is still significant after Holm (p = 0.034).
- **Does not hold up: the step-by-step increments.** Style pre-check on top of (a)+(b) (p = 0.044 uncorrected, 0.27 after Holm) and reasoning history on top of that (p = 0.40) are each in the right direction, but 31 tasks and 1 to 2 runs cannot separate them from noise. `docs/results.md` describes them as "+5.5 passes" and "+3.5 passes". Read those as point estimates whose 95% intervals include zero.
- **Does not hold up: "the fine-tuned reader helps the operator."** +0.018 reward, 7 tasks better and 7 worse. No detectable effect. Its pass@2 is higher (87% vs 74%) but its pass^2 is lower (45% vs 55%): it changes *which* tasks pass from run to run, not how many.
- **Does not hold up: "our local system beats Opus 5.5."** +0.032 (−0.014 to +0.081), p = 0.19. The honest claim is parity on this benchmark, as `docs/results.md` already says. Opus also got no harness tuning (section 7).
- **The final config's own interval is wide.** A 64.5% pass rate on 31 tasks is consistent with anything from 47% to 79%. Its pass^2 is 55%: of the 23 tasks it passed at least once, 6 failed in the other run (about one in four). Per category, leasing (18 tasks) passes 47% (27 to 69%), and the other categories have only 4 to 5 tasks each (ops 4/4 gives an interval of 51 to 100%).
- **Our loop vs NeMo's `simple_agent`, same prompt.** Our loop is ahead on reward (+0.11, p = 0.018 uncorrected, 0.12 after Holm) but not on pass/fail (9 vs 5 tasks). Likely real, but not established at this sample size.

To tell apart effects of about 0.03 reward (the size of the remaining open questions), we would need more tasks, not more repeats: run-to-run sd is already only 0.005 to 0.014, while the task-sampling interval is about ±0.04. That is what the realistic task set is for.

## 6. Scripted vs model-played renters

**Scripted (the default, every committed number).** Each renter is a list of lines keyed to a keyword classifier of the operator's last question (`gym/rentus_env/counterparts.py`). It is fully deterministic and cheap, and the expected values are the published reader labels. The cost is realism: an unusual phrasing, a confirmation or a correction can get silence (review flaw G4, partly fixed in v2 with fallback lines).

**Model-played (`llm_renter`, opt-in per counterpart).** `gym/rentus_env/llm_renter.py`. The organizers ruled that simulator models don't count toward the 33B budget (`docs/hackathon/updates.md`, 2026-10-17 12:50 ET). By default the renter is played by the same local Lightning endpoint. It never touches the running app. `simulator.base_url` / `model` per task, or `RENTER_SIM_BASE_URL` / `RENTER_SIM_MODEL`, point it at another model.

- Each renter has a **persona** (name, job, texting style, channel) and a hidden **truth sheet**: move-in date (optionally a vague phrasing given first, or a too-early date they give up once told the room isn't free yet), phone, head-count, reason, lease stance (yes, or ask for a shorter lease and then accept a year), language. **Behaviors:** vague-first, a price push in the opener, ghosting after N replies, and at most 2 facts per message.
- **The scorer is unchanged.** The converter (`gym/llm_renter_tasks.py`) keeps a task's world, faults and checks exactly and builds the truth sheet from the same expected values the checks test. So the checks compare the final world with the truth sheet.
- **Consistency comes from code, not from the model's memory.** A director in code tracks what has been revealed and adds a per-turn stage direction ("first time they ask for the date: answer only vaguely"). The model returns `{"reply", "revealed"}` under a JSON schema (vLLM structured output). A guard rejects a reply that states a different phone number, or confirms a wrong read-back, and retries once; a second failure falls back to a plain truthful templated line. The opening lines are the scripted task's own, verbatim.
- **Reproducibility.** Temperature 0, a fixed seed per renter (`simulator.seed`, overridable with `run_seeds.py --sim-seed` / `--sim-seed-follow`), thinking off. In a check of 3 identical 4-turn conversations under concurrent load, the facts were identical every time, but in 2 of the 4 turns at least one repeat worded the reply differently ("2 people total" vs "two of us"). That is batch-level numeric noise in vLLM. So the simulator is **consistent but not byte-reproducible**, and repeated runs need the pass^k / CI treatment above. Expect a little more variance than scripted mode.
- **Logging.** Every simulator turn is emitted as a `renter_message` event with actor `renter:<id>` (into the operator's event sink and into the transcript's `simulator.events`), and the full per-turn record (operator text, stage direction, raw outputs, rejections, fallbacks, latency) is saved under `simulator.renters` in `results/<run>/transcripts/<task>.json`.
- **Known limits.** The classifier label recorded as `asked` (used by the "does not re-ask" check) is still the keyword classifier, so that check behaves the same in both modes. A simulator can still be wrong in ways the guard doesn't catch (for example, a date given in an odd form). Read the transcripts of any surprising result. The renter is played by the same model family as the operator, which may make it easier to understand than a real person. The real-conversation dataset is the remedy, not a bigger simulator.

3/6 pass, mean reward 0.955 (one run, 6 tasks: a plumbing and realism check, not a score). What it shows:

- **The renter stuck to its truth sheet in all 54 turns**: 0 consistency rejections, 0 fallbacks, no ghosting. Every fact it gave matched the sheet, it never volunteered unasked facts, it played vague-first, the shorter-lease ask and the price push as written, and each turn was logged as a `renter_message` event from `renter:<id>`.
- **All three failures are operator errors that the scorer caught correctly.** Two of them are things a scripted renter could not have exposed in the same way. An echo guard was added after this run (it rejects a reply that repeats the operator's message and retries), and a test covers it. The demo was not rerun.

## 7. Known scorer and task limits

From `docs/task-review.md` (the full list, task by task):

- **v1 flaws that affect the committed numbers.** In 8 held-out tasks the renter's move-in date is before the room is free, so an operator that points this out gets no reply. "Reason recorded" passes as soon as any register row exists (G1). Style is scored on drafts the send tool refused (G2). That flatters the style pre-check row, which is one reason its increment is not significant above. Three tasks penalize correct behavior (for example banning the word "discount", or a one-shot publish fault that punishes a successful retry). v2 fixes these but is not yet approved.
- **Guards pass for an agent that does nothing.** `never` and `budget` checks give a do-nothing run 0.218 mean reward on v1 (0.291 on v2). Mean reward therefore starts well above 0, so read pass rate and pass^k alongside it.
- **The harness was tuned for Lightning.** Prompt v3, the guard and the style pre-check came from Lightning's train failures. The Opus reference got no tuning, so the comparison favors our system.
- **Small categories.** Listing, ops and recovery have 4 to 5 held-out tasks each, so per-category numbers are anecdotes with intervals 40 to 50 points wide.
- **Open owner decisions** (D1 to D5 in the review): the "6-month lease" refusal, whether accepting 6 months should complete the gate, the "males only" policy, the malformed fault that cannot corrupt rent, and whether confirmations count as re-asks.

## 8. Checklist for any new claim

1. Tasks, scorer and eval config unchanged, or a new version with its own baseline.
2. Designed on train, measured on held-out once the change is kept.
3. At least 2 seeded runs (`run_seeds.py`). Report pass rate with its Wilson interval, reward with its bootstrap interval, and pass^k.
4. Compare to the reference config with `stats.py --compare` (paired). Call it an improvement only if the paired interval excludes 0 after Holm across the comparisons made, and say how many comparisons that was.
5. If the result is surprising, read the transcripts.
